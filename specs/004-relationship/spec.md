## 承接关系

本 spec 是**服务级规格**，承接 `specs/002-wechat-style-chat` 的架构设计与「FR→服务承接表」中 relationship-svc 的职责边界。上游 002 定义了产品级需求（85 条 FR）与 7 服务拆分；本 feature 把 relationship-svc 的承接范围（002 的 FR-007~012、FR-049）细化为可独立实现、独立测试的服务级规格。**本 spec 不重复定义产品需求，只做服务级展开；冲突时以 002 与宪法为准。**

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 找到人并成为好友 (Priority: P1)

用户通过公开账号名搜索到想聊天的人，发出好友申请（可附言），对方接受后互为好友。

**Why this priority**: 好友关系是单聊（005-message）的前置——没有好友关系就无法建立一对一会话。它是首段切片「聊起来」的第二块基石。

**Independent Test**: 用户 A 搜索 B 的账号发起申请 → B 收到并接受 → A 的好友列表出现 B，可立即发起会话；不依赖消息服务。

**Acceptance Scenarios**:

1. **Given** A 与 B 尚无关系，**When** A 通过 B 的公开账号名搜索到 B 并发出好友申请（含附言），**Then** B 在「新的朋友」中看到该申请及附言
2. **Given** B 收到 A 的好友申请，**When** B 接受，**Then** 双方互为好友，各自好友列表出现对方，且具备发起单聊会话的能力
3. **Given** B 收到 A 的好友申请，**When** B 拒绝，**Then** 申请从待处理列表移除，A 收到拒绝结果，双方关系维持原状
4. **Given** A 已向 B 发出申请且 B 未处理，**When** A 再次向 B 发起申请，**Then** 系统拒绝重复申请并提示已有待处理申请

---

### User Story 2 - 好友备注与删除 (Priority: P2)

用户为好友设置单向备注，查看好友列表，删除好友。

**Why this priority**: 备注与删除是好友关系的日常管理能力，不阻塞核心的「加好友→聊天」闭环，属 P2。

**Independent Test**: A 给 B 设备注 → A 端显示备注而 B 端不受影响 → A 删除 B → 关系解除；不依赖消息服务。

**Acceptance Scenarios**:

1. **Given** A 与 B 是好友，**When** A 修改对 B 的备注，**Then** A 的界面与通讯录以备注显示 B，B 端不受影响
2. **Given** A 与 B 是好友，**When** A 查看好友列表，**Then** 看到所有好友（含备注与公开账号名）
3. **Given** A 与 B 是好友，**When** A 删除 B，**Then** 双方好友关系解除，既有单聊会话保留历史但不可再发送新消息

---

### User Story 3 - 拉黑与陌生人开关 (Priority: P2)

用户拉黑/解除拉黑，控制是否允许陌生人添加自己。

**Why this priority**: 拉黑是骚扰治理的底线（002 FR-011），陌生人开关承接身份服务的隐私能力（002 FR-049），属 P2 中合规与安全面最靠前的。

**Independent Test**: A 拉黑 B → B 发起申请/发消息被拒 → A 解除拉黑 → 恢复；A 关闭陌生人添加 → 陌生人发申请被拒。

**Acceptance Scenarios**:

1. **Given** A 拉黑 B，**When** B 尝试给 A 发好友申请或消息，**Then** 该行为被拒绝且 B 收到明确提示（原因类别）
2. **Given** A 与 B 有历史聊天记录，**When** A 拉黑 B，**Then** 双方仍可见既有历史记录
3. **Given** A 拉黑 B，**When** A 解除拉黑，**Then** B 恢复向 A 发起申请的能力
4. **Given** A 关闭「允许陌生人添加」，**When** 非好友向 A 发起申请，**Then** 申请被拒绝并提示对方未开启

---

### Edge Cases

- **重复申请**：A 已向 B 发出待处理申请时，MUST NOT 允许重复申请。
- **双向申请**：A、B 同时互相发起申请，接受其一后另一条申请 MUST 自动失效或合并，MUST NOT 产生两条冲突的好友关系。
- **拉黑与申请并存**：A 拉黑 B 后，B 既有的待处理申请 MUST 失效；A 解除拉黑后 B 需重新申请。
- **删除与重新申请**：删除好友后双方可重新发起申请（除非被拉黑）；删除 MUST NOT 影响既有单聊历史（保留但不可再发）。
- **拉黑的历史可见性**：拉黑 MUST NOT 影响双方既有历史聊天记录的可见性（002 FR-011）。
- **陌生人开关默认值**：陌生人添加开关默认允许（与身份服务一致），用户可随时切换。
- **并发接受**：B 同时处理多条申请时，每条 MUST 独立生效，MUST NOT 产生重复好友关系。

## Requirements *(mandatory)*

### Functional Requirements

**搜索与申请**（承接 002 FR-007~008）

- **FR-001**: 系统 MUST 支持按公开账号名精确搜索用户（搜索能力由 identity-svc 提供，客户端直连 identity 搜索；本服务消费 identity 的 `GetUser` 读取对方资料与陌生人开关）。
- **FR-002**: 用户 MUST 能发起好友申请并附上申请附言；接收方 MUST 能接受或拒绝。
- **FR-003**: 同一对用户之间同一时刻 MUST NOT 存在多条待处理申请；重复申请 MUST 被拒绝。
- **FR-004**: 接受好友申请后双方 MUST 互为好友，并立即具备发起单聊会话的能力（能力判定由本服务提供，会话由 message-svc 消费）。

**好友管理**（承接 002 FR-010）

- **FR-005**: 用户 MUST 能为好友设置单向备注；备注 MUST 仅对设置方可见，对方不可见且不受影响。
- **FR-006**: 用户 MUST 能查看自己的好友列表（含备注与公开账号名）。
- **FR-007**: 用户 MUST 能删除好友；删除后双方好友关系解除，既有单聊会话保留历史但不可再发送新消息。

**拉黑与隐私**（承接 002 FR-011、FR-049）

- **FR-008**: 用户 MUST 能拉黑与解除拉黑；拉黑 MUST 是单向行为。
- **FR-009**: 被拉黑方 MUST NOT 能发起好友申请、发起会话或发送消息，且系统 MUST 告知其被拒绝的原因类别；拉黑 MUST NOT 影响双方既有历史聊天记录。
- **FR-010**: 用户 MUST 能控制是否允许陌生人添加自己；关闭后非好友 MUST NOT 能向其发起申请。

**申请入口与授权**（承接 002 FR-012，供 message-svc 消费）

- **FR-011**: 系统 MUST 提供集中的「新的朋友」入口，区分待处理申请与历史申请。
- **FR-012**: 系统 MUST 提供「两人是否可互发消息」的授权校验能力，判定标准为「双方互为好友且未被任一方拉黑」，供 message-svc 在发单聊前调用。
- **FR-013**: 系统 MUST 在拒绝好友申请或消息时统一告知原因类别，枚举覆盖 FR-009（被拉黑）并扩展到「对方未开启陌生人添加 / 非好友」，MUST NOT 泄露更多状态信息。

**防骚扰与列表**（承接 002 与宪法 B 组）

- **FR-014**: 系统 MUST 对好友申请实施频率限制（账号 + IP 双维度），防骚扰刷申请，阈值在 plan 锁定。
- **FR-015**: 好友列表 MUST 分页返回，单次返回量有上限（默认 50、最大 1000），MUST NOT 无界返回。

### Key Entities

- **好友关系**：双方用户、建立时间、状态（正常 / 已删除）。
- **好友申请**：发起方、接收方、申请附言、状态（待处理 / 已接受 / 已拒绝）、发起时间、处理时间。
- **拉黑关系**：拉黑方、被拉黑方、拉黑时间、状态（拉黑中 / 已解除）。
- **备注**：归属方、被备注好友、备注内容、更新时间（单向，仅归属方可见）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 好友申请从发出到对方收到并显示的送达成功率 ≥ 99%。
- **SC-002**: 接受好友申请后，双方好友列表出现对方的一致性达 100%（MUST NOT 出现单向好友）。
- **SC-003**: 拉黑后，被拉黑方发起申请、会话、消息被拦截的成功率 100%。
- **SC-004**: 按公开账号名精确搜索命中目标用户的成功率 ≥ 99%。
- **SC-005**: 单向备注仅对设置方可见、对方不受影响的一致性 100%。
- **SC-006**: 删除好友后关系解除的一致性 100%（MUST NOT 残留单向好友）。

## Assumptions

- **上游承接**：本服务的职责边界以 002 的「FR→服务承接表」为准；搜索能力由 identity-svc 的 `SearchByPublicName` 提供，本服务不重复实现。
- **好友申请时效**：待处理申请默认 30 天自动过期（可调），过期后不可接受、需重新申请。
- **陌生人开关默认值**：默认允许陌生人添加（与 identity-svc 的 `allow_stranger_add` 默认值一致）。
- **删除语义**：删除好友是双向解除关系（002 US2 明确），非单向移除。
- **实现语言与工具链**：Go + 工具链（已登记于宪法 v2.7.0），本 spec 不绑定实现细节。
- **存储**：MongoDB（relationship 独占 database）；Redis 承载限流/缓存（非唯一事实来源）。
- **错误码**：复用 002 的 `contracts/error-registry.md`；本服务特有错误码（重复申请、拉黑拒绝、陌生人开关关闭）在 plan 锁定并登记注册表。

## 范围外（明确不包含）

- 单聊会话与消息收发——归 message-svc（005）。
- 群聊、通话、通知、治理处置——归 group / call / notification / moderation 各服务。
- 好友推荐、通讯录导入、手机号匹配好友——不在首段切片范围。
- 好友分组/标签——不在本期范围。
