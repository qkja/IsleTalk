## User Scenarios & Testing *(mandatory)*

### User Story 1 - 注册登录并开始使用 (Priority: P1)

新用户用手机号完成注册与身份验证，设置昵称头像后直接进入会话列表，
不需要等待人工审核或填写冗长资料。

**Why this priority**: 这是所有其他场景的前置条件。没有可用的身份，
任何消息能力都无法被使用；它是唯一一个"实现了它才有意义"的最小切片。

**Independent Test**: 在一台干净设备上完成手机号注册 → 验证码校验 → 昵称头像设置 →
  看到空的会话列表，整个流程可独立验证，不依赖任何消息功能。

**Acceptance Scenarios**:

1. **Given** 一个未注册的手机号，**When** 用户输入手机号并请求验证码，**Then** 系统在验证码有效期内接受正确验证码并完成注册
2. **Given** 已注册用户，**When** 输入正确凭证登录，**Then** 登录成功并进入会话列表，界面显示其最近的会话
3. **Given** 用户已登录，**When** 在另一台设备登录同一账号，**Then** 两个设备的会话同时有效，且后续消息在两端一致呈现
4. **Given** 用户不记得密码，**When** 通过手机号发起找回流程，**Then** 系统可通过手机号验证身份并重置密码，重置成功后旧会话全部失效
5. **Given** 用户在敏感设置页，**When** 执行更换手机号、修改密码等高风险操作，**Then** 系统要求先重新验证身份再执行
6. **Given** 用户希望提升信任等级，**When** 用户自愿提交身份信息完成实名，**Then** 系统在单独告知处理目的与保留期限并取得明示同意后受理，完成后用户获得信任等级标识与更高的使用额度
7. **Given** 用户未提交身份信息，**When** 用户使用应用，**Then** 用户可使用全部功能，不因未实名而受限

### User Story 2 - 找到人并成为好友 (Priority: P1)

用户通过公开账号名搜索到想聊天的人，发出好友申请，对方确认后成为好友，
并能对好友设置备注、按需拉黑。

**Why this priority**: 聊天应用的价值来自"和谁聊"。没有可靠的关系建立与保护机制，
后面的所有消息能力都无从触发；且拉黑与备注直接关系到隐私与骚扰治理。

**Independent Test**: 用户 A 搜索 B 的账号发起申请 → B 收到并接受 → A 的好友列表出现 B；
再由 A 拉黑 B，验证 A 的列表与后续行为变化，可独立验证。

**Acceptance Scenarios**:

1. **Given** 用户 A 与用户 B 尚无关系，**When** A 通过 B 的公开账号名搜索到 B 并发出好友申请，**Then** B 在"新的朋友"中看到该申请及申请附言
2. **Given** B 收到 A 的好友申请，**When** B 点击接受，**Then** 双方互为好友，各自的好友列表中出现对方，且可立即开始聊天
3. **Given** B 收到 A 的好友申请，**When** B 点击拒绝，**Then** 该申请从待处理列表移除，A 收到拒绝结果，且双方关系维持原状
4. **Given** A 与 B 已是好友，**When** A 修改对 B 的备注，**Then** A 的界面与通讯录中以备注显示 B，而 B 端不受影响
5. **Given** A 拉黑 B，**When** B 尝试给 A 发消息或发起好友申请，**Then** 该行为被拒绝且 B 收到明确提示
6. **Given** A 与 B 已有历史聊天记录，**When** A 拉黑 B，**Then** B 无法再发送消息，但双方仍能看到此前的历史聊天记录；A 仍可通过"清空聊天记录"自行移除本地记录，该操作不影响 B 侧
7. **Given** A 与 B 已是好友，**When** A 删除 B，**Then** 双方好友关系解除，既有单聊会话保留历史但不可再发送新消息
8. **Given** 用户 A 想更换公开账号名，**When** A 设置一个未被占用且不在保留期内的新账号名，**Then** 改名成功、新名字可被搜到，且旧名字在保留期内不能被他人使用
9. **Given** 一个未注册的手机号，**When** 用户尝试用手机号搜索，**Then** 系统不返回该手机号是否已注册的任何信息

### User Story 3 - 与好友一对一聊天 (Priority: P1)

用户与好友之间实时收发文本、图片与文件消息，能看到自己消息的发送与送达状态，
能撤回、引用、转发、删除自己的消息。

**Why this priority**: 这是产品的核心价值主张。单聊场景完整可用时，
应用已经是一个可用的即时通讯工具；群聊、通知等都是在它之上的扩展。

**Independent Test**: 两个账号互为好友 → 双向发送文本、图片、文件 → 校验送达与已读状态、
  撤回、引用、转发、删除的逐项行为，可独立验证。

**Acceptance Scenarios**:

1. **Given** A 与 B 是好友且均在线，**When** A 发送一条文本消息，**Then** B 的会话中在数秒内看到该消息，且 A 端状态由"发送中"变为"已送达"
2. **Given** B 打开了 A 的会话，**When** B 看到 A 的消息，**Then** A 端该消息的状态变为"已读"
3. **Given** A 发送了一条消息，**When** 该消息处于可撤回的时间窗内且 A 点击撤回，**Then** 双方界面均显示"对方撤回了一条消息"的占位提示，消息正文不再可见
4. **Given** A 发送消息时网络中断，**When** 发送失败，**Then** A 端明确看到失败状态并可手动重发，重发后不出现重复消息
5. **Given** B 离线，**When** A 连续发送多条消息后 B 重新上线，**Then** B 在会话中按原顺序收到全部离线期间的消息，无遗漏、无重复
6. **Given** A 想分享一条消息，**When** A 转发该消息给另一位好友 C，**Then** C 收到该消息且消息上标明来源为转发
7. **Given** A 想评论某条具体消息，**When** A 引用该消息回复，**Then** 双方界面同时呈现被引用消息的摘要与本次回复内容
8. **Given** A 与 B 同在一个群聊中，**When** B 读了 A 的一条消息，**Then** A 看到该消息的已读人数汇总随之增加，而 A 无法看到具体是谁读的

### User Story 4 - 多人群聊与群管理 (Priority: P2)

用户可以创建群聊、拉人进群、管理成员与群信息，群成员之间能像单聊一样收发消息；
群主可设置管理员并对成员禁言，违规内容可被限制。

**Why this priority**: 群聊是社交产品的第二高频场景，但它的价值建立在单聊已经可靠的前提上；
若单聊不稳定，群聊只会放大问题，因此排在单聊之后。

**Independent Test**: 创建群 → 邀请两名成员 → 群内互发消息 → 设置管理员 → 管理员禁言一名成员 →
  验证被禁言者无法发送、移除一名成员 → 验证被移除者无法再发送、群主转让后权限正确转移，可独立验证。

**Acceptance Scenarios**:

1. **Given** 用户 A，**When** A 从好友列表中选择多人创建群聊并填写群名称，**Then** 群聊创建成功，成员均收到入群通知
2. **Given** A 是群主，**When** A 移除成员 C，**Then** C 不再出现在群成员列表，且 C 在被移除后发送的消息不会送达其他成员
3. **Given** A 是群主，**When** A 转让群主给 B，**Then** B 获得群主权限（如踢人、改群公告），A 降为普通成员
4. **Given** A 是群主，**When** A 退出群聊，**Then** 群主身份自动转移给其他成员之一，且不会出现无人可管理的群
5. **Given** 群内有成员修改群公告，**When** 成员打开群资料，**Then** 群公告与修改人信息正确呈现
6. **Given** A 是群主，**When** A 设置 B 为管理员并对 C 执行禁言，**Then** B 可执行踢人与禁言等管理操作，且 B 的权限不超过群主
7. **Given** 成员 C 被禁言，**When** C 尝试发送消息，**Then** 消息未送达任何成员，C 看到明确的禁言原因与预计解除时间
8. **Given** 用户 C 从未与该群有过往来，**When** A 直接把 C 拉进群，**Then** C 立即成为成员、看到群资料与入群前历史消息，并收到载明邀请人与群名称的入群通知，且能立即退群

### User Story 5 - 找到并管理自己的会话 (Priority: P2)

用户的会话列表按最近活跃排序，显示每个会话的最新消息摘要与未读数量，
用户可搜索会话、置顶、免打扰、标记未读与删除会话。

**Why this priority**: 消息数量增长后，"快速回到要看的那个会话"决定了日常使用效率；
但它是管理面能力，排在消息收发本体之后。

**Independent Test**: 制造多个会话并产生不同未读数 → 校验排序、摘要、未读数 →
  执行搜索、置顶、免打扰、标记未读、删除 → 逐项验证列表行为，可独立验证。

**Acceptance Scenarios**:

1. **Given** 用户有多个会话且最近活跃时间不同，**When** 用户打开会话列表，**Then** 会话按最近活跃时间倒序排列，每条显示最新一条消息的摘要
2. **Given** 某个会话有 5 条未读消息，**When** 用户进入该会话，**Then** 未读数清零并被标记为已读
3. **Given** 用户希望突出某个会话，**When** 用户置顶该会话，**Then** 该会话固定显示在列表顶部，且置顶标识可见
4. **Given** 用户不想被打扰，**When** 用户对某会话设置免打扰，**Then** 该会话的新消息不触发声音或横幅提醒，但仍计入未读数
5. **Given** 用户记得聊天对象的昵称或备注，**When** 用户在搜索框输入关键词，**Then** 匹配的会话与联系人出现在结果中

### User Story 6 - 收到通知与离线消息提醒 (Priority: P2)

用户在不打开应用时仍能知道"谁找我有事"，并且能自行决定通知的打扰程度。

**Why this priority**: 通知是拉回用户的关键回路，但它是增强层——没有消息能力时通知也无内容可推；
且通知涉及平台权限与隐私权衡，需在核心能力稳定后接入。

**Independent Test**: 关闭应用后由另一账号发消息 → 收到通知 → 点击通知进入对应会话 →
  在隐私设置开启时验证通知不显示消息正文，可独立验证。

**Acceptance Scenarios**:

1. **Given** 用户已授权系统通知且处于离线状态，**When** 好友发来消息，**Then** 用户在设备上收到通知提醒，包含发送者与内容摘要
2. **Given** 用户开启了隐私模式，**When** 收到消息通知，**Then** 通知中不展示消息正文，仅提示"收到一条消息"
3. **Given** 用户对某会话设置了免打扰，**When** 该会话有消息到达，**Then** 不发出声音或横幅提醒
4. **Given** 用户在系统设置中关闭了本站点的通知权限，**When** 应用尝试发送通知，**Then** 应用给出引导用户前往系统设置的说明，而不是静默失败

### User Story 7 - 语音与视频通话 (Priority: P3)

用户能与好友或群成员发起语音/视频通话，看到对方来电提醒，接通后可静音、切换摄像头，
通话结束有记录，通话中断时双方都知道发生了什么。

**Why this priority**: 通话是"类微信"体验的重要组成，但它建立在消息与关系能力之上，
且媒体子系统（媒体协商、网络穿透、弱网恢复）的复杂度远高于消息，
排在消息本体之后，以免拖累 v1 的核心闭环。

**Independent Test**: 两个账号互为好友 → 发起 1v1 语音通话 → 对方响铃 → 接通并说话 →
  挂断并核对通话记录 → 断网制造异常 → 验证双方都感知到中断，可独立验证。

**Acceptance Scenarios**:

1. **Given** A 与 B 是好友且 B 在线，**When** A 发起语音或视频通话，**Then** B 在数秒内收到来电提醒（含发起人、音频/视频类型），B 可接听或拒接
2. **Given** 通话进行中，**When** 参与者切换静音、切换摄像头或将应用切到后台，**Then** 通话不中断且对端看到正确的状态变化
3. **Given** 通话进行中，**When** 一方网络中断或质量严重恶化，**Then** 双方界面都明确显示"连接中断/正在重连"并给出后续处理，不得静默结束
4. **Given** 一通通话结束，**When** 用户查看通话记录，**Then** 记录包含对方、类型、开始时间、时长与是否未接，用户可删除单条记录
5. **Given** A 与 B 在群聊中，**When** A 发起群语音或群视频通话，**Then** 群成员收到群通话提醒并可加入，参与人数达到上限时给出明确提示

### User Story 8 - 保护隐私与治理不良内容 (Priority: P3)

用户能控制自己的可见性（谁可以加我、谁可以看我的资料），能举报不良用户或内容，
并在被系统处置时能查到原因与申诉入口。

**Why this priority**: 隐私与治理是上线前必须具备的底线，但它是"防止出事"的保障，
而非用户主动使用的功能，因此在功能价值之后；但它 MUST NOT 被推迟到上线之后。

**Independent Test**: 关闭"允许陌生人添加"后由陌生账号发起申请应被拒绝；举报一名用户后
  在举报记录中可见且有处理状态，可独立验证。

**Acceptance Scenarios**:

1. **Given** 用户关闭了"允许陌生人添加我"，**When** 陌生账号发起好友申请，**Then** 申请被系统拒绝，且该账号无法直接发起会话
2. **Given** 用户希望隐藏自己的资料，**When** 用户调整资料的可见范围，**Then** 非好友按新设置看不到相应信息
3. **Given** 用户遇到骚扰或不良内容，**When** 用户举报该用户或消息并附上说明，**Then** 系统记录举报并向用户反馈已受理
4. **Given** 用户因被举报被系统限制，**When** 用户打开应用，**Then** 用户看到明确的处置原因、影响范围与申诉入口

---

### User Story 9 - 运营人员核实举报并执行处置 (Priority: P3)

平台运营人员在受限的后台查看举报与证据，判断是否违规并执行或解除处置；
所有操作留下可追溯的记录，被处置的用户能在应用内提交申诉并看到处理进度。

**Why this priority**: 没有承接方，FR-046、FR-047、FR-050 的状态就永远停在"已受理"，用户拿不到实际结果；
但它是内部治理回路，不是用户主动使用的功能价值，因此在所有用户故事之后。

**Independent Test**: 提交一条举报 → 运营后台出现该工单 → 运营执行封禁并填写依据 →
  平台用户端可见处置原因与申诉入口 → 用户提交申诉 → 由非原处置人复核并解除 → 全链路留痕可查，可独立验证。

**Acceptance Scenarios**:

1. **Given** 存在一条待处理举报，**When** 运营人员登录后台并查看该工单，**Then** 工单包含举报说明、证据与被举报对象的历史处置记录
2. **Given** 运营人员判定被举报对象违规，**When** 其执行封禁并填写处置依据，**Then** 被处置用户立即收到限制生效通知，应用内可见处置类型、原因与影响范围
3. **Given** 运营人员执行了处置，**When** 查询该处置的操作留痕，**Then** 可查到操作人、时间、对象、动作与依据，且该记录不可被删除或修改
4. **Given** 用户认为处置有误，**When** 用户在应用内提交申诉，**Then** 申诉进入待复核状态，由非原处置人的运营人员复核，结论对用户可见
5. **Given** 复核判定处置有误，**When** 运营解除处置，**Then** 用户的相关功能限制立即恢复，且解除动作同样留下留痕

### User Story 10 - 以偏好的语言使用应用 (Priority: P3)

用户首次使用可以选择界面语言，之后可以随时切换；日期、数字、货币按其语言与地区习惯呈现，
放大系统字体后界面依然可用，读屏软件能读出关键控件与状态。

**Why this priority**: 国际化与无障碍是产品覆盖面的基本盘，不是差异化能力；
本期不做也不影响核心聊天闭环的价值交付，但它一旦缺席就无法靠后续补丁补齐（文案未外置、布局未适配放大），因此仍放在功能价值之后、而非可延后到上线后。

**Independent Test**: 首次进入选择英文 → 全程走一遍核心路径确认无中文残留 → 切回中文 →
  调整系统字体到最大档 → 校验关键页面可读可用，可独立验证。

**Acceptance Scenarios**:

1. **Given** 用户首次启动应用，**When** 用户选择界面语言，**Then** 之后所有界面文案均为所选语言，且该选择在后续启动时保持
2. **Given** 用户已在使用应用，**When** 用户在设置中切换语言，**Then** 界面文案即时切换，且不残留上一语言的文案；日期与数字按当前语言与地区习惯呈现
3. **Given** 用户将系统字体放大到设备支持的最大档，**When** 用户浏览会话列表与聊天界面，**Then** 关键内容不被截断或遮挡，主要功能仍可完成
4. **Given** 用户使用读屏软件，**When** 用户浏览会话列表与发送消息，**Then** 关键控件、消息内容与消息状态均能被朗读，状态不只依赖颜色表达

---

### Edge Cases

**消息与可靠性**

- **消息在对方阅读前被撤回**：撤回必须对双方一致生效，不能出现"发送方已撤回、接收方仍可见"的中间态。
- **撤回时间窗的判定时钟不一致**：设备时间被修改时，撤回窗口的判定 MUST NOT 依赖客户端本地时间。
- **发送瞬间对方已离线**：消息进入离线队列，不丢失，且在对方上线后按原顺序补发。
- **发送瞬间自己被移出群聊**：该消息 MUST NOT 送达群内其他成员，且发送方收到明确失败原因。
- **同一条消息的网络重投**：重试 MUST NOT 让对方看到两条相同消息（幂等）。
- **消息在多端之间的顺序不一致**：两台设备 MUST 呈现一致的会话顺序。
- **网络切换（Wi-Fi ↔ 蜂窝）：** 切换过程中已发送的消息 MUST NOT 丢失或重复。

**群组**

- **群成员数达到上限**：新建群或拉人时 MUST 给出明确上限提示，而不是静默失败。
- **群主退出**：群主身份 MUST 自动转移，不得出现无管理者的群。
- **删除好友与群聊并存**：删除好友 MUST NOT 影响双方共同的群聊关系。
- **群管理员被撤销后**：其已执行的禁言 MUST 有明确的可撤销路径。
- **被拉入陌生群**：用户被拉入一个从未与之有过往来的群时 MUST 收到载明邀请人与群名称的明确通知，且 MUST 能立即退群；邀请频率 MUST 受限制，不得被用于反复骚扰。

**通话**

- **通话中一方切换网络（Wi-Fi ↔ 蜂窝）**：通话 MUST 尝试无缝迁移或给出明确的中断提示，MUST NOT 静默结束。
- **群通话中成员陆续进出**：进出 MUST NOT 影响其余参与者，且界面 MUST 反映当前参与者名单。
- **通话中对方发来消息**：消息 MUST 正常送达并通知，MUST NOT 因通话状态被吞掉。
- **弱网下的通话质量**：质量恶化 MUST 有可感知的降级表现（画面降清晰度、改纯语音）或明确提示。
- **被呼叫方正在另一个通话中**：MUST 给出"对方忙线"的明确状态，MUST NOT 无限响铃。

**规模与治理**

- **万级并发在线时的在线状态广播**：状态变更 MUST NOT 以逐条广播的方式放大为写放大。
- **群消息量突增**：大群的成员变更 MUST NOT 导致全群消息延迟劣化。
- **成员退群后的已读计数**：成员退群后其历史阅读位置 MUST 保留以维持计数一致，但 MUST NOT 再计入新增的已读人数；该处理 MUST 对群内其他成员完全不可见。
- **批量注册与刷号**：注册与验证码接口 MUST 有频率限制，异常行为 MUST 被识别并阻断。
- **封禁与解禁的生效时机**：处置 MUST 在合理时间内生效，且 MUST NOT 影响用户查看自己的历史消息。

**通用**

- **超大文件 / 超长文本**：超出允许大小或长度时 MUST 在发送前被拦截并说明限制。
- **拉黑与既有会话的交互**：拉黑后既有单聊 MUST 立即禁止发送，但双方的历史聊天记录 MUST 均保留可见；拉黑方清除本地记录的动作 MUST NOT 影响对方。
- **对方注销账号**：会话中的对方身份 MUST 有明确的失效呈现，且不出现空白或报错。
- **多端同时登录时改密码**：旧会话 MUST 在合理时间内全部失效。

**标识与查找**

- **账号名冲突**：两名用户同时设置同一账号名时 MUST 只有一人成功，另一人收到明确的冲突提示；MUST NOT 出现两个账号同时"拥有"同一名字的状态。
- **旧账号名被尝试占用**：处于保留期的账号名 MUST 被拒绝使用，且提示信息 MUST NOT 泄露原持有者的身份信息。
- **连续试探账号名**：短时间内高频试探账号名是否存在的行为 MUST 被识别并限流，避免被用于枚举他人标识。

**内容处置**

- **举报后的处置时效**：自举报提交起 MUST 有明确的首响时限，超时 MUST 触发升级处理，MUST NOT 出现"已受理但无人推进"的悬空状态。
- **处置不追溯未举报内容**：对某用户或某条内容的处置 MUST NOT 自动扩大为对其全部历史内容的批量处置，除非用户本人主动发起批量清理。

**治理与申诉**

- **误判处置后的申诉**：用户对处置提出申诉时 MUST 由非原处置人复核并及时解除误判；解除 MUST 同步撤销相关的功能限制。
- **运营人员权限的回收**：运营人员的权限 MUST 在其职责结束时及时失效，其历史操作留痕 MUST 保留可查。

**实名与信任**

- **实名提交中断**：实名提交过程中断（网络失败或用户中途退出）时 MUST NOT 产生"已实名"状态，MUST 允许重新提交，且 MUST NOT 残留半份身份信息。
- **撤回实名后的额度回落**：用户撤回实名后信任等级立即降级，此前放宽的使用额度 MUST 同步回落，MUST NOT 保留已撤销的放宽状态。

**通话证据边界**

- **举报通话骚扰时的证据来源**：用户提交的是对通话的描述，系统可核对的只有通话元数据（时间、时长、参与方、结束原因）；MUST NOT 调取通话音视频内容作为证据，也 MUST NOT 因缺少音视频而拒绝受理举报。

## Requirements *(mandatory)*

### Functional Requirements

**账号与身份**

- **FR-001**: 系统 MUST 支持用户以手机号注册，验证码在有效期内仅可成功使用一次。
- **FR-002**: 注册完成后用户 MUST 可直接登录使用，MUST NOT 需要人工审核或线下审批。
- **FR-003**: 系统 MUST 支持登录、退出登录、以及用户主动注销全部设备会话。
- **FR-004**: 用户 MUST 能修改昵称、头像与个性签名。
- **FR-005**: 更换手机号、修改密码、注销账号等高风险操作 MUST 要求重新验证身份。
- **FR-006**: 用户 MUST 能主动注销账号，系统 MUST 按既定保留策略处理其留下的数据并在界面明确告知。

**好友与关系**

- **FR-007**: 用户 MUST 能通过公开账号名精确搜索到目标用户；系统 MUST NOT 提供按手机号搜索用户的能力，手机号 MUST 仅用于验证码验证身份。
- **FR-008**: 用户 MUST 能发起好友申请并附上申请附言；接收方 MUST 能接受或拒绝。
- **FR-009**: 接受好友申请后双方 MUST 互为好友，并立即具备发起单聊会话的能力。
- **FR-010**: 用户 MUST 能为好友设置备注、查看好友列表、删除好友。
- **FR-011**: 用户 MUST 能拉黑与解除拉黑。拉黑 MUST 是单向行为：被拉黑方 MUST NOT 能发起好友申请、发起会话或发送消息，且系统 MUST 告知其被拒绝的原因类别；拉黑 MUST NOT 影响双方既有的历史聊天记录——双方仍可见历史。
- **FR-012**: 系统 MUST 提供集中的"新的朋友"入口，区分待处理申请与历史申请。

**会话与消息**

- **FR-013**: 用户 MUST 能与任一好友建立单聊会话，无需对方事先同意。
- **FR-014**: 用户 MUST 能创建群聊、邀请成员、移除成员、退出群聊；邀请成员为直接生效（细则见 FR-081）。
- **FR-015**: 群主 MUST 能转让群主身份、修改群名称与群公告；群主退出时群主身份 MUST 自动转移给其他成员之一。
- **FR-016**: 用户 MUST 能发送文本消息。
- **FR-017**: 用户 MUST 能发送图片消息。
- **FR-018**: 用户 MUST 能发送文件消息；系统 MUST 对文件类型与大小设限并在超限时于发送前拦截并说明限制。
- **FR-019**: 系统 MUST 为每条消息呈现发送状态（发送中 / 已送达 / 已读 / 失败）与失败原因；已读的呈现方式 MUST 按会话类型区分（细则见 FR-083）。
- **FR-020**: 用户 MUST 能在允许的时间窗内撤回自己发送的消息，撤回后双方看到一致的占位提示。
- **FR-021**: 用户 MUST 能转发消息（单条或批量）到好友或群聊，并标明来源。
- **FR-022**: 用户 MUST 能引用回复特定消息，并 MUST 能删除自己本地的消息记录而不影响对方。
- **FR-023**: 会话列表 MUST 展示每个会话的最新消息摘要、未读数量与最近活跃时间，并 MUST 按最近活跃时间倒序排列。
- **FR-024**: 用户 MUST 能对会话执行置顶、免打扰、标记未读与删除会话操作。
- **FR-025**: 系统 MUST 支持按昵称、备注、群名称搜索会话与联系人。
- **FR-026**: 同一账号在多个设备登录时，各端 MUST 呈现一致的消息内容与顺序。

**送达、可靠性与离线**

- **FR-027**: 在线接收方 MUST 实时收到消息；离线接收方 MUST 在重新连接后收到离线期间的全部消息。
- **FR-028**: 消息投递 MUST 是幂等的：重试、网络重投 MUST NOT 导致接收方看到重复消息。
- **FR-029**: 消息发送失败时系统 MUST 明确告知用户并提供重发入口，重发 MUST NOT 产生重复。
- **FR-030**: 系统 MUST 保证消息不被静默丢失；发生无法恢复的失败时 MUST 明确告知用户而非假装成功。
- **FR-031**: 消息排序 MUST 稳定，乱序到达的消息 MUST 按其固有时序呈现。

**通知**

- **FR-032**: 用户 MUST 能接收新消息的系统通知，且 MUST 能在应用内按会话开关通知。
- **FR-033**: 通知内容 MUST 随隐私设置变化：开启隐私模式时通知 MUST NOT 暴露消息正文。
- **FR-034**: 系统通知权限被关闭时，应用 MUST 引导用户前往系统设置，MUST NOT 静默失败。

**语音与视频通话**

- **FR-035**: 用户 MUST 能对好友发起 1v1 语音通话与视频通话，接收方 MUST 能接听或拒接。
- **FR-036**: 用户 MUST 能在群聊中发起群语音通话与群视频通话，参与人数 MUST 有明确上限，达到上限时 MUST 明确提示。
- **FR-037**: 通话中用户 MUST 能静音、切换摄像头、切换前后台；此类切换 MUST NOT 中断通话。
- **FR-038**: 被呼叫方正处于另一通话中时，发起方 MUST 得到"对方忙线"的明确状态，MUST NOT 无限响铃。
- **FR-039**: 通话结束后系统 MUST 生成通话记录（含对方、类型、开始时间、时长、是否未接），用户 MUST 能删除单条记录。
- **FR-040**: 通话过程中网络中断或质量严重下降时，系统 MUST 向双方明确提示并尝试恢复，MUST NOT 静默结束通话。
- **FR-041**: 通话质量 MUST 可被观测（建立耗时、端到端延迟、抖动、丢包、异常中断率），异常 MUST 触发告警并配有处置手册。
- **FR-042**: 系统 MUST NOT 向用户提供通话录音或录像功能，界面上 MUST NOT 出现录制入口。为排查通话质量而采集的音视频片段 MUST 仅在受控环境内短期保留、MUST 去标识化、最大保留期 MUST 不超过 7 天，且 MUST NOT 对用户可见、亦 MUST NOT 作为对用户的举报证据被调取。

**群管理与内容治理**

- **FR-043**: 群主 MUST 能设置与撤销群管理员；管理员 MUST 能执行禁言与移除成员等管理操作，且其权限 MUST NOT 超过群主。
- **FR-044**: 群主与管理员 MUST 能对群成员禁言；被禁言成员 MUST 收到明确的禁言原因与预计解除时间。
- **FR-045**: 群成员规模 MUST 有明确上限（默认不超过 500 人），达到上限时 MUST 明确提示。
- **FR-046**: 系统 MUST 支持对违规用户实施限制（禁言、限制登录、封禁），并 MUST 向被处置用户说明处置原因、影响范围与申诉入口。
- **FR-047**: 用户 MUST 能在应用内查看针对自身的处置记录与申诉进度。
- **FR-048**: 用户可见的公开内容（昵称、个性签名、群名称、群公告）MUST 在发布前被校验，明显违规内容 MUST 被拦截。

**隐私与治理**

- **FR-049**: 用户 MUST 能控制是否允许陌生人添加自己，以及个人资料的可见范围。
- **FR-050**: 用户 MUST 能举报用户、群聊、单条消息或通话骚扰并提交说明；系统 MUST 记录举报并向用户反馈受理状态；通话骚扰的核查 MUST 仅基于通话元数据（时间、时长、参与方、结束原因），MUST NOT 调取通话音视频内容。
- **FR-051**: 应用的日志、诊断信息与统计上报 MUST NOT 包含消息正文、完整手机号或其他完整个人身份信息。
- **FR-052**: 通话记录、举报记录与处置记录 MUST 与消息正文同等对待，属敏感数据，MUST 受保留期限与访问控制约束。

**范围边界**

- **FR-053**: 本版本 MUST NOT 包含朋友圈/动态、公众号或小程序、支付、位置共享、语音条消息与桌面端原生客户端；这些能力 MUST NOT 以任何形式出现在界面上。
- **FR-054**: 消息传输 MUST NOT 采用端到端加密；系统 MUST 在用户可见的隐私说明中如实告知传输与存储方式。
- **FR-055**: 系统 MUST NOT 把同一能力以多套不一致的实现并列提供给用户（例如同一功能在不同终端的行为不同且无说明）。

**客户端形态**

- **FR-056**: iOS 与 Android 客户端 MUST 完整支持注册登录、好友关系、单聊与群聊、消息状态与撤回、通知、语音与视频通话。
- **FR-057**: Web 端 MUST 仅提供账号安全与申诉入口，MUST NOT 承载完整聊天体验；其提供的功能 MUST 在移动端有等价入口。
- **FR-058**: 每个被支持的终端 MUST 能独立完成注册登录、建立好友关系、收发消息、查看会话列表这四条核心路径。

**用户接入与规模**

- **FR-059**: 系统 MUST 开放公开注册路径（除受邀的内测通道外），MUST NOT 要求人工审批。
- **FR-060**: 系统 MUST 对注册、登录与验证码下发实施频率限制与异常行为识别，刷号与暴力尝试 MUST 被自动阻断。
- **FR-061**: 系统 MUST 在用户规模与并发量达到目标（十万级注册用户、万级同时在线）时仍满足既定服务目标与质量门禁。

**运营后台与执行**

- **FR-062**: 系统 MUST 提供受限的平台运营后台，使运营人员能查看举报工单与证据、执行处置（警告、禁言、限制登录、封禁）并解除处置。
- **FR-063**: 运营后台 MUST 与终端用户界面分离，MUST 走独立鉴权与授权；运营人员的每次查看与处置操作 MUST 留下审计留痕（操作人、时间、对象、动作、依据），该留痕 MUST NOT 被应用侧删除或修改。
- **FR-064**: 用户 MUST 能对自身处置提交申诉；系统 MUST 记录受理、复核与结论状态并对用户可见；申诉 MUST 由不同于原处置人的运营人员复核。

**国际化与可访问性**

- **FR-065**: 系统 MUST 支持简体中文与英文两种界面语言；用户 MUST 能在应用内选择界面语言，该选择 MUST 被记住并在后续启动时生效。
- **FR-066**: 所有用户可见文案 MUST 外置为可翻译资源，MUST NOT 硬编码在代码中；新增界面语言 MUST NOT 要求改动业务逻辑。
- **FR-067**: 时间 MUST 以明确时区存储与展示；日期、数字与货币 MUST 按当前语言与地区习惯格式化；切换语言后 MUST NOT 残留未翻译的文案。
- **FR-068**: 界面 MUST 满足平台原生无障碍要求：系统字体放大到设备支持的最大档时关键内容不截断、功能不不可达；读屏软件能完整朗读关键控件、消息内容与消息状态；状态与错误 MUST 有颜色之外的表达；关键页面 MUST 逐条复核 WCAG 2.2 AA 成功判据。

**实名与敏感个人信息**

- **FR-069**: 用户 MUST 能在注册后自愿提交身份信息完成实名；未实名的用户 MUST 能使用全部功能，实名 MUST NOT 成为使用任何功能的前提。
- **FR-070**: 采集身份信息前，系统 MUST 以单独同意方式取得用户明示同意，并 MUST 事先告知处理目的、范围、保留期限与可能后果；未经单独同意 MUST NOT 采集。
- **FR-071**: 身份信息 MUST 静态加密存储，MUST NOT 出现在日志、指标、链路追踪、错误响应与任何对外接口中，展示时 MUST 脱敏；运营人员查看未脱敏身份信息 MUST 需要单独授权且其查看行为 MUST 留痕。
- **FR-072**: 身份信息 MUST 仅用于实名与由此产生的信任等级目的，MUST NOT 用于内容推荐、画像外销或任何未经单独同意的用途。
- **FR-073**: 用户 MUST 能随时查看自己的实名状态并撤回实名；撤回后 MUST 删除身份信息、信任等级降级，且因信任等级而放宽的使用额度 MUST 同步回落。
- **FR-074**: 身份信息 MUST 有明确的保留期限与到期删除机制；用户注销账号时 MUST 按该机制处理并 MUST 告知用户处理方式。

**标识与发现**

- **FR-075**: 系统 MUST 为每个用户分配一个全局唯一、不可变的内部账号 ID；该 ID MUST NOT 展示为可搜索的公开标识，MUST NOT 提供任何修改途径。
- **FR-076**: 用户 MUST 能设置一个独立的公开账号名以供他人搜索。公开账号名与内部账号 ID MUST 是两个不同的标识；系统 MUST 保证账号名唯一，冲突 MUST 在设置时立即报错并提示，且 MUST 校验保留词，MUST NOT 出现两个账号同时占用同一账号名的状态。
- **FR-077**: 用户 MUST 能修改其公开账号名，此修改 MUST NOT 影响内部账号 ID；新账号名 MUST 重新通过唯一性与保留词校验，且 MUST 受冷却期限制（距上次修改的间隔不得短于规定时长），以限制抢注与批量试探。
- **FR-078**: 用户放弃的账号名 MUST 进入保留期，保留期内 MUST NOT 被其他用户使用，以防旧标识被抢注后冒充本人；保留期长度 MUST 在 `plan.md` 确定（默认 90 天）并对用户可见。

**内容风控口径**

- **FR-079**: 聊天正文 MUST NOT 做事前的关键词或规则拦截，消息 MUST 照常投递；违规正文的发现与处置 MUST 走事后路径（FR-050 举报 → FR-062 运营后台 → FR-046 限制与封禁）。
- **FR-080**: 系统 MUST 在用户可见的社区规范中如实告知"聊天正文不在发送时拦截、违规内容在被举报后核查"这一处置口径，MUST NOT 让用户误以为存在实时过滤。

**群成员准入**

- **FR-081**: 邀请成员 MUST 直接生效：被邀请人 MUST 立即成为群成员，MUST 收到载明邀请人与群名称的入群通知，并 MUST 被明确告知可随时退群；被邀请人入群后 MUST 能看到群资料与入群前的历史消息。
- **FR-082**: 邀请行为 MUST 受频率限制（同一被邀请人短时间被拉入群聊的次数、同一群主的邀请频率），超出上限时 MUST 拒绝并向邀请人说明原因，防止该能力被用于骚扰。

**已读回执**

- **FR-083**: 1v1 会话中消息 MUST 显示精确的已读与未读状态；群聊会话中 MUST 只显示已读人数汇总，MUST NOT 提供逐人已读名单。
- **FR-084**: 每个群成员的阅读位置 MUST 独立记录以支撑汇总计数；该逐人数据 MUST 仅用于计数，MUST NOT 以任何形式暴露给其他群成员或普通用户界面。

**检索范围**

- **FR-085**: 本版本 MUST NOT 提供消息正文（聊天内容）的全文检索；该能力 MUST 另开 feature 目录走完整的 Spec Kit 流程实现，其服务边界、索引方案、中文分词处理方式，以及"搜索结果本身属敏感数据"这一隐私边界，MUST 在该 feature 的 spec 与 plan 中确定。MUST NOT 为了本期交付而在本版本内以临时方案实现。

### Key Entities

- **用户账号**：使用者的身份载体。属性含不可变的内部账号 ID、公开账号名、手机号、昵称、头像、个性签名、可见范围设置、注册与注销状态、风控处置状态。手机号属于敏感个人信息，对外展示与日志中 MUST 脱敏。
- **设备会话**：用户的一次登录实例。属性含设备标识、登录时间、最近活跃时间、是否被远程下线。是"强制下线""多端一致"两类能力的基础。
- **好友关系**：两个用户之间的关系。属性含发起方、状态（待处理 / 已是好友 / 已拒绝 / 已拉黑）、备注、申请附言。单向发起、双方确认。
- **群聊**：多人会话容器。属性含群名称、群公告、群主、管理员列表、成员列表、成员上限。群主是唯一的权限持有者，管理员是其受限代理。
- **群成员身份**：用户在某个群中的角色与限制。属性含角色（群主 / 管理员 / 成员）、禁言状态与解除时间、加入时间。禁言与群角色是群内治理的载体。
- **会话**：一段持续的对话，是会话列表的基本单元。可分为单聊会话与群聊会话，属性含参与方、最后一条消息摘要、未读数、最近活跃时间、置顶与免打扰标记。
- **消息**：一次表达。属性含所属会话、发送者、内容（文本 / 图片 / 文件）、固有时序、发送状态、送达与已读状态、是否已撤回、是否为转发或引用及其引用目标。消息正文属敏感内容。
- **通话**：一次实时音视频交互。属性含主叫与被叫方或参与方列表、通话类型、开始与结束时间、时长、结束原因（正常挂断 / 拒接 / 忙线 / 异常中断 / 未接）。通话记录属敏感数据。
- **通知订阅**：用户对某个会话的通知偏好。属性含是否开启、是否免打扰、通知内容是否显示正文。
- **举报与处置记录**：治理动作的载体。属性含举报对象、举报人、举报说明、证据、受理状态与处理结论；针对用户的处置含处置类型、原因、影响范围、起止时间、处置人与申诉进度。
- **运营人员账号**：具备平台治理权限的内部使用者账号。属性含所属角色、权限范围、可执行的处置类型、有效状态。其全部行为 MUST 留痕，且职责结束时权限 MUST 及时失效。
- **界面语言偏好**：用户选择的界面语言。属性含语言标识、来源（跟随系统或用户指定）、最近一次生效时间。是文案外置与地区格式化的驱动依据。
- **实名信息**：用户自愿提交的身份信息。属性含身份标识、认证状态、提交时间、保留期限。属敏感个人信息，MUST 加密存储，仅在授权范围内可读。
- **信任等级**：由实名状态派生的用户属性。属性含等级、对应额度、在受限维度上的放宽项。实名撤回后 MUST 同步降级。
- **账号名占用**：公开账号名的分配与保留记录。属性含账号名、当前占用者、释放时间、保留截止时间。是防止旧标识被抢注冒充的载体。
- **阅读位置**：某成员在某会话中已读到的位置。属性含会话、成员、已读至的消息、最近更新时间。是计算群聊已读人数的底层数据，MUST NOT 对其他成员可见。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新用户从打开应用到发出第一条消息的完成时间中位数 ≤ 3 分钟。
- **SC-002**: 至少 95% 的新用户能在无人工协助的情况下完成"注册 → 添加好友 → 发出第一条消息"全流程。
- **SC-003**: 在线状态下消息从发送到对方可见的延迟，95 分位 ≤ 2 秒。
- **SC-004**: 离线消息在对方重新连接后 100% 可达，全量抽样验证无丢失、无重复、无乱序。
- **SC-005**: 系统对消息的持久化完整性达到"读到的就是写下的"——抽样对账不出现内容或顺序不一致。
- **SC-006**: 消息发送失败时，100% 的失败在用户界面显式可见，不存在用户以为发出但对方收不到的情况。
- **SC-007**: 包含 100 个会话的账号，首次进入会话列表的可见时间 ≤ 1.5 秒。
- **SC-008**: 拉黑生效后，被拉黑方发起的消息 100% 被拒绝，且用户能明确区分"被拒绝"与"网络故障"。
- **SC-009**: 撤回操作在 100% 的情况下对发送方与接收方呈现一致的最终状态。
- **SC-010**: 会话列表的未读计数与实际未读消息数保持一致，抽样核对偏差为 0。
- **SC-011**: 举报提交后 100% 在用户侧可见受理状态，处置结论可追溯。
- **SC-012**: 跨端登录的同一账号在各设备上呈现一致的消息内容与顺序。
- **SC-013**: 应用崩溃导致会话中断的比例低于 0.1%。
- **SC-014**: 95% 的用户能在首次使用的 5 分钟内，通过会话列表与搜索定位到目标会话，并在该会话中找到并回复一条历史消息。
- **SC-015**: 在双方网络正常条件下，1v1 语音通话的接通率 ≥ 95%。
- **SC-016**: 从点击发起通话到对方收到来电提醒的耗时中位数 ≤ 3 秒。
- **SC-017**: 语音通话端到端延迟 95 分位 ≤ 400 毫秒，视频通话 ≤ 500 毫秒。
- **SC-018**: 通话异常中断时 100% 被通话双方感知，不存在"静默挂断"。
- **SC-019**: 禁言生效后，被禁言者的消息 100% 未送达群内其他成员。
- **SC-020**: 明显违规的公开内容（昵称、个性签名、群名称、群公告）在发布前被拦截的比例 100%。
- **SC-021**: 被处置用户 100% 能在应用内查到处置原因与申诉入口。
- **SC-022**: 系统在 10,000 用户同时在线时，消息送达延迟 95 分位仍 ≤ 2 秒。
- **SC-023**: 注册用户规模达到 100,000 时，服务月度可用性 ≥ 99.9%。
- **SC-024**: 500 人规模群聊中，消息零丢失、零重复、顺序零错乱。
- **SC-025**: 举报从提交到首次处理的中位时长 ≤ 24 小时；处置结论 100% 可追溯到具体操作人与依据。
- **SC-026**: 100% 的平台处置（封禁、限制登录）在应用内向用户展示原因与申诉入口。
- **SC-027**: 100% 的申诉由非原处置人复核，复核结论对用户可见。
- **SC-028**: 英文界面下未翻译的残留文案数量为 0；全部用户可见文案 100% 外置于代码之外。
- **SC-029**: 系统字体放大到设备支持的最大档时，100% 的关键页面不出现内容截断、遮挡或功能不可达。
- **SC-030**: 关键页面的 WCAG 2.2 AA 成功判据复核覆盖率 100%；Web 端账号安全与申诉页 100% 通过自动化可访问性检查。
- **SC-031**: 采集身份信息前 100% 取得单独同意；100% 的用户可在应用内查看与撤回自己的实名状态。
- **SC-032**: 抽样验证中，身份信息在日志、指标、链路追踪、错误响应与对外接口中的出现次数为 0。
- **SC-033**: 用户撤回实名或注销账号后，身份信息在 30 天内完成删除或不可逆处理（法定留存除外，且已告知用户处理方式）。
- **SC-034**: 拉黑操作后，双方历史聊天记录的完整率 100%（抽样比对拉黑前后记录条数一致，无误删）。
- **SC-035**: 系统中不存在可供用户使用的通话录制入口；用于质量排查的音视频片段 100% 去标识化且最大保留期 ≤ 7 天；通话骚扰举报的核查 100% 仅基于通话元数据。
- **SC-036**: 按公开账号名精确搜索命中目标用户的成功率 ≥ 99%；MUST NOT 出现两个账号同时占用同一账号名的状态。
- **SC-037**: 系统 MUST NOT 通过响应内容、错误码或提示文案区分"该手机号是否已注册"；抽样验证两种情形下的响应一致。
- **SC-038**: 用户可见的社区规范中 100% 说明聊天正文的事后处置口径；举报提交后 24 小时内完成首次核查的比例 ≥ 95%，MUST NOT 出现举报无后续动作的情形。
- **SC-039**: 用户被拉入群聊后 100% 收到载明邀请人与群名称的入群通知；被拉入后用户立即退群的成功率 100%。
- **SC-040**: 群聊已读人数汇总与实际已读成员数一致（抽样比对偏差为 0）；任何群成员 MUST NOT 能获取其他成员的逐人已读明细。

## Assumptions

- **产品定位**：IsleTalk 是一个面向个人与小型社群的即时通讯应用，对标主流即时通讯工具的核心体验（好友关系、单聊、群聊、消息状态、通知、语音与视频通话），不追求平台化的商业能力。
- **服务边界**：本规格覆盖的是产品能力集合，不含服务清单。依宪法原则 V，微服务拆分（按业务边界）及其拆分理由 MUST 在本 feature 的 `plan.md` 中固定；单个服务若被独立实现，MUST 另开 feature 目录补充其规格。
- **终端范围**：首发以 iOS 与 Android 移动端为主，Web 仅承担账号安全与申诉。桌面端原生客户端不在本版本范围。
- **通话范围**：1v1 语音与视频通话、群语音与群视频通话均在本版本范围内。媒体服务（采集、编解码、混流、网络穿透、弱网恢复）是独立子系统，其服务边界与选型 MUST 在 `plan.md` 中论证；群视频通话是本版本最重的子项，`plan.md` MUST 明确其降级路径与是否分阶段交付。**不提供通话录音与录像功能**；为排查通话质量而采集的音视频片段按 FR-042 处理，其 7 天最大保留期是保守默认值，`plan.md` MUST 在不损害排查能力的前提下论证是否可以收紧。
- **用户接入与规模**：开放公开注册，面向十万级注册用户、万级同时在线设计。该规模要求注册与登录风控、限流、容量规划、内容治理流程在 `plan.md` 中逐条落实（对应宪法 C、D、E 组）。
- **国际化**：首发支持简体中文与英文两种界面语言。英文界面不等于面向英文市场运营；面向欧盟用户提供服务时才适用 GDPR 一套义务，该判断与应对 MUST 在 `plan.md` 中写明。
- **可访问性口径**：宪法 G 组的 WCAG 2.2 AA 条款与"自动化可访问性检查纳入 CI"是以 Web 界面为前提的，而本期移动端为原生实现。本期以"平台原生无障碍规范 + WCAG 2.2 AA 判据逐条复核"落地（FR-068），自动化检查覆盖 Web 端页面；若要严格要求对原生界面执行 Web 自动化检查工具，MUST 以 MINOR 版本修订宪法明确口径与工具。
- **实名的定位与触发条件**：实名是**可选**的信任增强手段，不是使用任何功能的前提；未实名用户保留全部功能。实名带来的差异是信任等级标识与受限维度上更高的使用额度（消息发送频率、新增好友数、创建群聊数等），具体额度 MUST 在 `plan.md` 论证并对用户可见。实名同时是将来满足监管实名要求的技术路径：一旦产品转为面向境内公众提供实时音视频类服务或进入商业化运营，MUST 重新评估实名是否转为强制，并把结论与存量用户补验方案写入 `plan.md`。
- **端到端加密不在本期范围**：宪法 G 组已将端到端加密列入"当前阶段明确不引入"清单，其触发条件（需与外部组织交换敏感数据，或监管对特定场景提出加密要求）本期尚未达成。因此本规格以服务端可读为前提，并要求在隐私说明中如实告知用户。
- **内容审核**：本期不引入自动化内容审核引擎，但 MUST 具备发布前的基础校验、举报入口、举报受理与人工处置流程（宪法 G 组「运营与支持」要求）。聊天正文本身不做事前拦截（FR-079），违规正文的处置走事后路径——这使发送链路保持轻量、避免正常聊天被关键词误伤，代价是违规内容在被举报前会先流出去。由于本期面向公开注册用户且含实时音视频能力，MUST 在上线前依据届时适用的法规评估"仅事后处置"这一口径是否可接受，并把评估结论与必要的补偿控制写入 `plan.md`。
- **即时可达**：本期假定系统具备让在线消息即时送达、无需用户手动刷新的能力（具体实现方式与选型在 `plan.md` 论证）。
- **多端一致**：本期假定支持同一账号在多个终端同时在线，并要求跨端消息内容与顺序一致（同步机制在 `plan.md` 论证）。
- **文件传输**：本期文件消息限定为常规文档与图片类文件，限制大小上限并做类型校验；断点续传与云盘级文件分享不在本期范围。语音条消息同样不在本期范围。
- **数据保留**：消息与会话的保留期限、可撤回的时限窗口、禁言的最长时长、未读计数的清空规则，由 `plan.md` 结合宪法 B 组的数据保留与 PII 清单要求确定，并在产品内可见。
- **检索范围**：本期只提供会话与联系人搜索（FR-025）。消息正文全文检索不在本版本范围，另开 feature 走完整 Spec Kit 流程（FR-085）；该能力的搜索结果本身是敏感数据（能查出谁与谁说过什么），其隐私边界与索引方案 MUST 在那个 feature 中先行确定。
- **语言与运行环境**：实现语言尚未确定，由 `plan.md` 按宪法 A 组论证选型并登记工具链；本规格不绑定任何语言、框架、存储或传输协议。
- **本地依赖**：本地开发所需的基础设施按宪法 A 组以容器化编排启动、镜像版本固定；具体镜像清单与编排文件在 `plan.md` 确定。

## 范围外（明确不包含）

以下能力在本版本内不实现，也不预留可见入口：

- 朋友圈 / 动态 / 状态
- 公众号 / 小程序 / 开放平台
- 支付、钱包、交易
