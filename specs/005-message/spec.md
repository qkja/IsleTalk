## 承接关系

本 spec 是**服务级规格**，承接 `specs/002-wechat-style-chat` 的架构设计与「FR→服务承接表」中 message-svc 的职责边界。上游 002 定义了产品级需求；本 feature 把 message-svc 的承接范围（002 的 FR-013、FR-016~020、FR-023~026、FR-028）细化为可独立实现、独立测试的服务级规格。**本 spec 不重复定义产品需求，只做服务级展开；冲突时以 002 与宪法为准。**

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 与好友一对一收发消息 (Priority: P1)

用户与好友之间收发文本、图片与文件消息，看到自己消息的发送与送达状态，对方已读后状态更新。

**Why this priority**: 这是产品的核心价值主张。单聊收发可用即意味着应用已成为一个可用的即时通讯工具。

**Independent Test**: 两个账号互为好友 → 双向发送文本、图片、文件 → 校验送达与已读状态，可独立验证。

**Acceptance Scenarios**:

1. **Given** A 与 B 是好友且均在线，**When** A 发送一条文本消息，**Then** B 的会话中在数秒内看到该消息，且 A 端状态由「发送中」变为「已送达」
2. **Given** B 打开了 A 的会话，**When** B 看到 A 的消息，**Then** A 端该消息的状态变为「已读」
3. **Given** A 发送一张图片消息，**When** 发送完成，**Then** B 收到并可见该图片
4. **Given** A 发送一个文件消息，**When** 文件大小在允许范围内，**Then** B 收到并可下载该文件；超限时 A 在发送前收到拦截提示

---

### User Story 2 - 撤回与离线补发 (Priority: P1)

用户能撤回时间窗内的消息，离线期间的消息在上线后按原顺序补发，无遗漏无重复。

**Why this priority**: 撤回是消息可靠性的底线（发错能收回），离线补发保证多端一致与消息不丢（SC-004/005）。

**Independent Test**: A 撤回一条消息 → 双方看到占位提示；B 离线期间 A 连发多条 → B 上线后按序收到全部。

**Acceptance Scenarios**:

1. **Given** A 发送了一条消息，**When** 在可撤回时间窗内 A 点击撤回，**Then** 双方界面均显示「对方撤回了一条消息」占位，消息正文不再可见
2. **Given** A 发送消息时网络中断，**When** 发送失败，**Then** A 端明确看到失败状态并可手动重发，重发后不出现重复消息
3. **Given** B 离线，**When** A 连续发送多条消息后 B 重新上线，**Then** B 按原顺序收到全部离线消息，无遗漏、无重复

---

### User Story 3 - 会话列表与管理 (Priority: P2)

会话列表展示最新消息摘要、未读数量与最近活跃时间，用户能置顶、免打扰、删除会话。

**Why this priority**: 会话列表是多会话场景的导航入口，不阻塞核心收发，属 P2。

**Independent Test**: 多会话下查看列表（摘要/未读/倒序）→ 置顶 → 免打扰 → 删除，逐项验证。

**Acceptance Scenarios**:

1. **Given** 用户有多个会话，**When** 查看会话列表，**Then** 看到每个会话的最新消息摘要、未读数量与最近活跃时间，按最近活跃倒序排列
2. **Given** 用户对某会话执行置顶，**When** 查看列表，**Then** 该会话排在列表顶部
3. **Given** 用户对某会话执行免打扰，**When** 该会话来新消息，**Then** 不触发通知提醒（仍计入未读）
4. **Given** 用户删除某会话，**When** 之后对方发来新消息，**Then** 该会话重新出现在列表中

---

### Edge Cases

- **消息幂等**：客户端重发同一条消息（相同 message_id）时 MUST 去重，MUST NOT 产生重复消息（FR-028）。
- **离线补发顺序**：离线期间的消息 MUST 按会话内 seq 单调递增补发，MUST NOT 乱序（FR-031）。
- **撤回时间窗**：撤回窗口由服务端时钟判定，MUST NOT 依赖客户端时间（FR-020）。
- **撤回非本人**：撤回 MUST 校验发送者身份，非本人撤回 MUST 被拒绝。
- **文件超限**：文件类型/大小超限 MUST 在发送前拦截并说明限制（FR-018）。
- **消息授权**：发消息前 MUST 校验双方互为好友且未被拉黑（调 relationship CanMessage），非好友或被拉黑 MUST 拒绝发送。
- **多端一致性**：同一账号多设备登录时，各端 MUST 呈现一致的消息内容与顺序（FR-026）。
- **附件访问控制**：图片/文件附件 MUST 仅对会话参与者（互为好友）可见，非好友或被拉黑方 MUST NOT 能访问。
- **撤回后的摘要展示**：撤回的消息在会话列表「最新消息摘要」中 MUST 显示「撤回了一条消息」占位，MUST NOT 显示原文。

## Requirements *(mandatory)*

### Functional Requirements

**会话与消息**（承接 002 FR-013、FR-016~018）

- **FR-001**: 用户 MUST 能与任一好友建立单聊会话，无需对方事先同意。
- **FR-002**: 用户 MUST 能发送文本消息。
- **FR-003**: 用户 MUST 能发送图片消息。
- **FR-004**: 用户 MUST 能发送文件消息；系统 MUST 对文件类型与大小设限并在超限时于发送前拦截并说明限制。

**状态与可靠性**（承接 002 FR-019/020/028）

- **FR-005**: 系统 MUST 为每条消息呈现发送状态（发送中 / 已送达 / 已读 / 失败）与失败原因。消息由服务端成功接收后标记「已送达」（delivered），接收方上报已读后标记「已读」（read）。
- **FR-006**: 用户 MUST 能在允许的时间窗内撤回自己发送的消息，撤回后双方看到一致的占位提示。
- **FR-007**: 消息 MUST 以客户端生成的幂等键（message_id）去重，重发 MUST NOT 产生重复消息。

**会话列表与管理**（承接 002 FR-023/024）

- **FR-008**: 会话列表 MUST 展示每个会话的最新消息摘要、未读数量与最近活跃时间，按最近活跃时间倒序排列。
- **FR-009**: 用户 MUST 能对会话执行置顶、免打扰、标记未读与删除会话操作。

**多端一致与授权**（承接 002 FR-026，宪法 E 组）

- **FR-010**: 同一账号多设备登录时，各端 MUST 呈现一致的消息内容与顺序。
- **FR-011**: 发消息前 MUST 校验双方互为好友且未被拉黑（消费 relationship-svc 的 CanMessage），非好友或被拉黑 MUST 拒绝发送。
- **FR-012**: 消息拉取 MUST 分页（默认 50、上限 1000），MUST NOT 无界返回。

### Key Entities

- **会话（Conversation）**：会话标识、类型（单聊）、参与者、最近消息摘要、未读数量、置顶/免打扰/已删除标记、最近活跃时间。
- **消息（Message）**：消息标识（幂等键）、会话标识、发送者、类型（文本/图片/文件）、正文或附件引用、会话内序号（单调递增）、发送时间、状态（发送中/已送达/已读/失败）、是否撤回。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 消息从发送到对方收到并显示的送达成功率 ≥ 99%。
- **SC-002**: 已读状态的准确性 100%（对方打开会话后，发送方状态 MUST 变为已读）。
- **SC-003**: 撤回后双方看到一致占位提示的一致性 100%。
- **SC-004**: 离线期间的消息补发 MUST 无遗漏、无重复、无乱序（100%）。
- **SC-005**: 同一账号多设备的消息内容与顺序一致性 100%。
- **SC-006**: 消息幂等去重通过率 100%（相同 message_id 重发 MUST 不产生重复）。

## Assumptions

- **上游承接**：本服务的职责边界以 002 的「FR→服务承接表」为准；发消息前授权校验由 relationship-svc 的 `CanMessage` 提供，本服务不重复实现好友关系。
- **撤回时间窗**：默认 2 分钟（可调），由服务端时钟判定。
- **文件限制**：图片默认 ≤10MB（格式 jpg/png/gif/webp）、文件默认 ≤100MB（可调），超限发送前拦截。
- **附件存储**：图片/文件正文存对象存储（002 待办），消息仅存附件引用（key）；客户端直传对象存储，message-svc 不中转附件正文；对象存储选型属 002 待办。
- **实现语言与工具链**：Go + 工具链（已登记于宪法 v2.7.0），本 spec 不绑定实现细节。
- **存储**：MongoDB（message 独占 database）；Redis 承载未读计数/会话缓存（非唯一事实来源）。
